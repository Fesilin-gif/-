# Портфолио — личный сайт

Третье, самостоятельное приложение репозитория. Соседние проекты
(PCMarket в корне и `project-amb/`) оно не трогает: свои зависимости,
своя сборка, свои изображения — всё внутри `portfolio/`.

Next.js 15 (App Router) · React 19 · TypeScript. Без GSAP, Lenis, видео
и 3D: заставка держится на одном `requestAnimationFrame`-цикле и CSS
`transform`.

## Запуск

```bash
cd portfolio
npm install
npm run dev      # http://localhost:3001
npm run build
npm start
npm run lint     # tsc --noEmit
```

Порт 3001 — чтобы можно было поднимать одновременно с соседними
приложениями, которые заняли 3000.

## Что происходит на экране

1. При открытии сайта, на белом фоне, почти сразу проявляется (мягким
   затуханием занавески, не рывком) арка с девушкой обычного, целиком
   видимого размера — в её проёме уже виден пейзаж. Под аркой — надпись
   «Загрузка…» с тонкой бегущей полоской (без выдуманных процентов:
   точный прогресс загрузки картинок браузер не даёт, поэтому полоска
   просто показывает, что что-то происходит). Заголовка и медальонов на
   этом экране нет вовсе. Загрузка держится не меньше 4 секунд с
   открытия страницы, даже если картинки готовы раньше (иначе на
   быстрой сети или с картинками из кэша не успеть понять, что вообще
   происходит) — см. `INTRO.minLoadingMs` в `lib/scene.ts`.
2. Как только пройдены и эти 4 секунды, и картинки для заставки готовы
   — полоска исчезает.
3. Без клика и без прокрутки сам начинается влёт: арка и девушка
   увеличиваются и уходят за края экрана, а пейзаж, который был виден
   в проёме, плавно занимает экран целиком. Прокрутка страницы на это
   время заблокирована — случайный скролл не может сбить кадр влёта.
   Пропустить заставку нельзя — заходя на сайт, её видят каждый раз.
4. Влёт заканчивается — и это весь итог страницы: только пейзаж, во
   весь экран, неподвижной картинкой. Ни заголовка, ни выбора проектов
   здесь сегодня нет (см. «Что заполнить» ниже — решить, чем закончить
   страницу, предстоит отдельно, когда появятся настоящие проекты).
   Прокручивать страницу дальше некуда — она ровно в размер экрана.
5. При `prefers-reduced-motion: reduce` (или без JS) заставки нет
   вовсе: пейзаж открыт сразу, обычной статичной картинкой на весь
   экран. Если какая-то картинка так и не загрузится, через 6 секунд
   сайт всё равно откроется (см. «Готовность картинок» ниже).

## Как устроена заставка

Один и тот же `<img>` с пейзажем на всём протяжении — сначала виден
через прозрачный проём арки, затем занимает экран целиком. Ни смены
источника, ни второй копии, ни перекрёстного затухания.

Устроено это через общий контейнер `.rig`, размером с натуральный кадр
арки (1122×1402). Внутри него, в этих же координатах:

- **`.rig__window`** — неподвижная обёртка панорамы, ровно того же
  размера, что и `.rig`. У неё ПОСТОЯННАЯ маска — `mask-size: 100% 100%`,
  `mask-position: 0 0`, никогда не пересчитывается. Маска —
  `arch-opening-mask.png`, готическая форма проёма (тот же
  геометрический источник, что и сама арка: альфа-канал
  `arch-transparent.png`);
- **панорама** — `<img>` внутри `.rig__window`, со своим собственным
  `transform`, который каждый кадр анимации пишет `Intro.tsx` (см. ниже,
  «панорама двух состояний») — маски это не касается вообще, у обёртки
  своя, постоянная система координат;
- **фигура арки** (`arch-transparent.png`) — тот же кадр 1122×1402, без
  собственного `transform`: она просто совпадает с координатами `.rig`
  пиксель в пиксель, но её непрозрачность гаснет к концу влёта.

`.rig` двигается одним `transform` (`translate` + `scale`), который
каждый кадр анимации пишет `Intro.tsx` — им одновременно масштабируются
и обёртка панорамы (вместе со своей постоянной маской), и фигура арки.

Это, по сути, та же геометрия, что раньше вела отъезд камеры по
прокрутке в более ранней версии этой страницы, только пройденная в
обратную сторону (внутрь окна, а не наружу) и по времени
(`requestAnimationFrame`), а не по `scrollTop`. Направление задают два
готовых состояния из `computeLayout` (`lib/scene.ts`): `arch` —
стартовый, контейнерный кадр арки обычного размера (влёт начинается
отсюда, `t=0`) и `rigStart` — кадр настолько огромный, что даже его
проём с запасом перекрывает весь экран (влёт заканчивается здесь,
`t=1`): в этом состоянии камень и девушка далеко за краями экрана, а
пейзаж внутри проёма — ровно то же самое, что `fitCoverFocused` дал бы
для простого полноэкранного фона, точный обратный расчёт
(`landscapeStartRect`), а не приближение на глаз. Дойдя до `t=1`, `.rig`
и панорама застывают в этом положении — `position: fixed`, тот же
элемент `<img>` — и это весь итог страницы: другого содержимого под
ней сегодня нет (см. «Что происходит на экране» выше).

**Панорама двух состояний.** Местоположение самой панорамы внутри
`.rig__window` — не константа, а функция `t`. На входе (`t=0`) —
`localViewRect`: панорама, подогнанная точно под форму проёма. На
выходе (`t=1`) — `landscapeStartRect`. Между ними — тот же приём, что и
у самого `.rig`: геометрический интерфит масштаба и линейный интерфит
опорной точки (фокуса), чтобы кадр стягивался к одной точке, а не
«плыл».

Панорама едет почти по тому же `t`, что и `.rig`, но с небольшой
отсрочкой старта (`INTRO.landscapeSettleFrom` в `lib/scene.ts`, сейчас
`0.08`): до этой точки она стоит на месте, в самом безопасном
(заведомо накрывающем проём) положении, и только потом начинает
сжиматься к `landscapeStartRect`. Значение подобрано опытным путём —
плотным прогоном скриншотов по всей длительности влёта на нескольких
пропорциях экрана (обычный десктоп, телефон, широкий монитор): если
вести панораму строго тем же `t`, что и `.rig`, на широких экранах
чуть-чуть не хватает — проём растёт быстрее, чем успевает сжаться
панорама, и на мгновение виден белый холст; если отложить старт
заметно позже — не хватает уже с другого края, ближе к концу влёта.
Найденное значение — компромисс между этими двумя крайностями, а не
точный расчёт (в отличие от `localViewRect`/`landscapeStartRect`,
которые считаются точно). `localViewRect` дополнительно берёт финальный
кадр панорамы с запасом (`FINAL_VIEW_MARGIN = 2.2`, по центру) — та же
подушка безопасности на середине перехода.

Маска держится на отдельной неподвижной обёртке, а не на самой
панораме, — иначе на входе, где локальный масштаб панорамы специально
маленький (чтобы совпасть с широким полноэкранным кадром при огромном
`.rig`), получаются тысячи пикселей `mask-size`, а это ломает рендер
CSS-маски в Chromium (проверено на практике).

**Появление арки и девушки.** Маска `arch-opening-mask.png` не
вычитает силуэт девушки — только истинный контур каменного проёма
(свод по кривой альфа-канала, ниже свода — по измеренному постоянному
положению стен, независимо от того, где именно сидит девушка на
исходной фотографии). Так пейзаж внутри проёма никогда не оставляет
белую дыру в форме девушки, даже если бы её фигура была не полностью
непрозрачна (см. «Если понадобится пересобрать маску проёма» ниже).

### Готовность картинок и минимальная длительность загрузки

Заставке нужны две картинки — панорама и фигура арки — плюс маска
проёма (она не `<img>`, а CSS `mask-image`, готовность которой
проверяется отдельной, синтетической `Image()`). `Intro.tsx` следит за
готовностью каждой и запускает влёт только тогда, когда готовы все три
И прошло не меньше `INTRO.minLoadingMs` (4000 мс) с открытия страницы
— в зависимости от того, что наступит позже. Порог отсчитывается от
открытия страницы, а не от готовности картинок: на быстрой сети или
с картинками из кэша браузера готовность может наступить почти сразу,
и без этого порога посетитель не успевает понять, что вообще
происходит, прежде чем экран сменится. Если какая-то картинка так
и не загрузится (медленная сеть, битая ссылка), через 6 секунд
готовность считается наступившей принудительно — сайт не должен
виснуть вечно.

Отдельная тонкость: страница отрисована на сервере, и браузер
начинает грузить `<img>` сразу по разбору HTML, ещё до гидратации —
на быстром или кэшированном файле `load` успевает произойти раньше,
чем React вообще навесит обработчик `onLoad`, и тот в этом случае не
сработает никогда. Поэтому готовность проверяется не только через
`onLoad`/`onError` в разметке, но и синхронно, сразу после монтирования,
через `img.complete` — обычное свойство DOM, ему всё равно, когда его
прочли.

Ещё одна: сам `.rig` и его дети `<img>` в разметке присутствуют с
самого начала (иначе браузер не начнёт их грузить заранее) — а не
`display: none`/`visibility: hidden`/`opacity: 0` на самом `.rig`
(на практике скрытие `.rig` любым из трёх способов давало один и тот
же брак на первый кадр после появления — маска проёма ещё не готова,
и проём на мгновение пуст). Пока страница отрисована на сервере, но
JS ещё не выполнился (или выполнился, но раскладка ещё не посчитана),
`.rig` держит закрытым `.intro__curtain` — сплошной холст поверх него.
Но держит его не всё время ожидания, а буквально пару кадров: как
только `Intro.tsx`, синхронно перед первой отрисовкой, успевает
посчитать стартовый кадр арки (`t=0`) и применить его transform'ом
(см. `positioned` в компоненте), и одновременно готова маска проёма
(синтетическая `Image()`, см. выше) — класс `.intro--arch-visible`
плавно, за 620 мс, гасит занавеску, и арка проявляется в своём точном
положении. Дальше, пока идёт остаток ожидания, она так и стоит на
месте (при resize/повороте экрана раскладка пересчитывается заново,
чтобы не дёрнуться в момент начала влёта, см. обработчик `resize` в
`Intro.tsx`) — никакого повторного появления или скачка в момент,
когда сама загрузка заканчивается и начинается влёт.

## Что заполнить

Сегодня заставка — вся страница: за влётом идёт только пейзаж, без
заголовка и без выбора проектов (см. «Что происходит на экране» выше).
Когда появятся настоящие проекты, решить предстоит и то, чем страница
заканчивается — заголовком и медальонами (см. «О `Medallions.tsx`»
ниже), отдельными разделами или чем-то ещё.

1. **Проекты** — `lib/projects.ts`, массив `PROJECTS`. Сейчас там три
   пустых слота: ни названий, ни описаний, ни ссылок не придумано.
   У каждого проекта есть `id` (он же будущий сегмент адреса кейса),
   `title`, `summary`, `caseHref`, `liveHref`, необязательный
   `medallion` (кадр внутри круга) и необязательный `windowView` (было
   для переключения вида в окне арки — сегодня нигде не используется,
   см. «О `Medallions.tsx`» ниже).
2. **Кейсы** — страницы `app/case/[id]/page.tsx` по `id` из списка.
3. **Метаданные** — `app/layout.tsx`: имя, описание, домен. Там сейчас
   нейтральная заглушка без выдуманного названия.

## О `Medallions.tsx`

Компонент ряда медальонов (выбор проекта) и поле `windowView` у
проекта в `lib/projects.ts` (переключение вида в окне арки в
зависимости от выбранного медальона) — рабочий код из более ранней
версии страницы, где за отъездом камеры следовали заголовок «Какой ваш
выбор?» и сам ряд. Сегодня `Intro.tsx` ничего из этого не подключает:
после влёта на странице только пейзаж, а окно арки — часть исключительно
самой заставки, вид в нём всегда один и тот же по умолчанию. Код и
стили (в `scene.css`, раздел «Медальоны») не убрал — пригодятся, когда
появится, чем закончить страницу после настоящих проектов, — но и не
выдавал их за то, что сегодня реально на экране.

## Если понадобится пересобрать маску проёма

`arch-opening-mask.png` не рисуется руками — это результат обработки
альфа-канала `arch-transparent.png`. Пересобирать нужно только если
появится новый файл арки. Два шага:

1. Найти истинный проём — топологически замкнутую прозрачную область
   внутри непрозрачного силуэта арки и девушки, самую крупную по
   площади (так отсеивается шум вроде мелких просветов в волосах).
2. **Заполнить силуэт девушки**, если она перекрывает часть проёма —
   маска не должна вычитать её форму (иначе там, где маска исключает
   пейзаж, а фигура арки ещё не полностью непрозрачна, был бы виден
   голый холст). В своде (там, где стрельчатый свод сужается) доверяем
   измеренному контуру как есть — там девушка ещё не мешает. Ниже
   свода стены проёма прямые и вертикальные — их положение известно
   заранее (`ARCH.opening.x`/`width`), заполняем строку до них целиком,
   независимо от того, где именно на фотографии сидит девушка.

```python
from PIL import Image
import numpy as np
from scipy.ndimage import binary_fill_holes, label

im = Image.open('arch-transparent.png').convert('RGBA')
w, h = im.size
alpha = np.asarray(im)[:, :, 3]
opaque = alpha > 10
holes = binary_fill_holes(opaque) & ~opaque
labels, _ = label(holes)
sizes = np.bincount(labels.ravel()); sizes[0] = 0
window = labels == np.argmax(sizes)

# opening/cap_end — те же доли, что ARCH.opening и порог свода в lib/scene.ts
opening = {'x': 0.328, 'y': 0.1148, 'width': 0.3529, 'height': 0.5278}
y0, y1 = int(opening['y'] * h), int((opening['y'] + opening['height']) * h)
x_lo, x_hi = int(opening['x'] * w), int((opening['x'] + opening['width']) * w)
cap_end = int(0.3 * h)  # ниже — доверяем не кривой, а известному прямому краю стен

filled = window.copy()
for y in range(y0, y1):
    if y < cap_end:
        xs = np.where(window[y])[0]
        if xs.size == 0:
            continue
        lo, hi = xs.min(), xs.max()
    else:
        lo, hi = x_lo, x_hi
    filled[y, lo:hi + 1] = True

added = filled & ~window  # там, где раньше была девушка — теперь полностью открыто
out = np.zeros((h, w, 4), dtype=np.uint8)
out[..., :3] = 255
out[..., 3] = np.where(window, 255 - alpha, 0)  # мягкий край антиалиасинга арки
out[..., 3] = np.where(added, 255, out[..., 3])  # заполненное — полностью открыто
Image.fromarray(out, 'RGBA').save('arch-opening-mask.png')
```

И заодно поправьте в `lib/scene.ts` константы `ARCH.content` и
`ARCH.opening` (доли ширины/высоты файла) и, если стрельчатый свод у
новой арки другой формы, порог `0.3` внутри `OPENING_RECT_SAFE`
(комментарий рядом объясняет, как его измерить) — он же используется
и здесь, при пересборке маски. Измеряются они по тому же альфа-каналу,
но руками, отдельным разовым скриптом, не частью сборки.

Если у новой фотографии другие пропорции опаcной (пропущенной) части
проёма или другая обрезка, может понадобиться заново подобрать и
`INTRO.landscapeSettleFrom`/`FINAL_VIEW_MARGIN` — тем же прогоном
скриншотов по всей длительности влёта, что описан выше.

## Мелочи, о которых стоит знать

- Холст намеренно не `#ffffff`, а `#fefefe` — так задано изначальными
  иллюстрациями; на итоговой композиции (прозрачный PNG поверх белого
  холста) разницу не видно, но так исторически сложилось при первой
  сборке сцены, менять без причины не стал.
- В файле арки вокруг рисунка широкие прозрачные поля (слева и справа
  по ~18%). Стартовый кадр арки вписывает в рамку не файл, а саму
  живопись (`ARCH.content`), иначе арка выходит заметно мельче, чем
  могла бы.
- Полезно, но не обязательно: кадры для медальонов — квадратные, от
  240×240, по одному на проект. Пока их нет, в круге стоит номер.
